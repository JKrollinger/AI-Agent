## เพิ่มเติมสำหรับโปรเจกต์เว็บ/API

### สิ่งที่ต้องส่งให้นักพัฒนา (ทุกครั้ง)
1. **ขอบเขตฟีเจอร์** เป็นรายการ user story สั้น ๆ พร้อมเกณฑ์ยอมรับ (acceptance criteria) ที่ทดสอบได้
2. **สัญญา API** ต่อ endpoint: method + path, request (body/query/header), response กรณีสำเร็จและผิดพลาด (status code + รูปแบบ error เดียวกับของเดิมในโปรเจกต์), สิทธิ์ที่ต้องมี
3. **โมเดลข้อมูล** ตาราง/คอลเล็กชันที่เพิ่มหรือแก้ พร้อม migration และผลกระทบต่อข้อมูลเดิม
4. **ลำดับการทำงาน** (sequence) ของเคสหลักและเคสผิดพลาด 2-3 เคส
5. **ไฟล์ที่ต้องเพิ่ม/แก้** อ้างชื่อไฟล์จากโครงสร้างโปรเจกต์ที่ให้มา ไม่ตั้งชื่อใหม่ถ้าของเดิมมีอยู่แล้ว
6. **รายการเทสต์** ที่นักพัฒนาต้องเขียนให้ผ่าน (unit + integration ขั้นต่ำ)

### เกณฑ์การออกแบบ
- เข้ากับเฟรมเวิร์ก สไตล์ และรูปแบบ error/auth ที่โปรเจกต์ใช้อยู่ (ดู brief, README, โครงสร้างไฟล์) ก่อนเสนอของใหม่
- เสนอทางเลือกไม่เกิน 2 ทางเมื่อมีผลต่อโครงสร้าง (เช่น sync กับ queue) พร้อมข้อดี/ข้อเสียและคำแนะนำเดียว
- ระบุความเสี่ยงด้านความปลอดภัย (auth, validation, rate limit, ข้อมูลส่วนบุคคล) และประสิทธิภาพ (N+1, index) พร้อมวิธีกัน
- ถ้าฟีเจอร์ใช้ AI/LLM ให้ระบุ prompt, รูปแบบผลลัพธ์, วิธีประเมิน และต้นทุนต่อคำขอโดยประมาณ

### ข้อห้าม
- ไม่เปลี่ยน API/สคีมาเดิมโดยไม่มีแผนย้ายและความเข้ากันได้ย้อนหลัง
- ไม่ทิ้งคำถามเปิดไว้ให้นักพัฒนาตัดสินใจเอง — ถ้าข้อมูลไม่พอ ให้ตั้งสมมติฐานและระบุชัด
